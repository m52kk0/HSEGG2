# Решения

Таблица для защиты: что добавили, что убрали и почему. Каждое решение объяснимо, включая
отклонения от ТЗ — они отмечены отдельно.

---

## Продукт: что добавили

| Решение | Почему |
| --- | --- |
| Вердикт одной фразой сверху экрана | Абитуриент пришёл за ответом «хватит ли баллов», а не за таблицей. Сначала ответ, потом причина, потом данные. |
| Зоны «Мечта / Цель / Запасной» вместо процентов | Вероятность по открытым данным посчитать нельзя: нет распределения баллов подавших, числа согласий и динамики отзывов. Процент был бы выдумкой в решении, которое принимается один раз. |
| Запас баллов «+12» / «−8» | Проверяемая величина: видно, откуда взялась. Процент проверить нельзя. |
| Приоритет 1 подписан «Хочу больше всего» | Главное непонимание абитуриентов: зачисляют на высший приоритет, по которому проходишь, поэтому мечту ставить первой — бесплатно. Слово «приоритет» этого не объясняет. |
| Предупреждение «подушка на первом приоритете обесценивает всё ниже» | Самая частая и самая дорогая ошибка в заявлении. |
| Предупреждение о нескольких регионах | Переезд — расходы, о которых узнают после зачисления. Сервис денег не считает, но промолчать о них нельзя. |
| Симуляция «Что будет, если…» | Показывает механику зачисления на своём же плане: текстовая цепочка по приоритетам, не вероятность. |
| План Б с четырьмя ветками | Вердикт «Высокий риск» без продолжения — это тупик. Допнабор, платное с переводом, колледж и год на подготовку — реальные пути со сроками. |
| «Похожие направления» с разницей одной фразой | Абитуриент не видит разницы между 15.03.04, 27.03.04 и 13.03.02. Это и есть настоящий вопрос выбора. |
| Кнопка «Открыть пример плана» на входе | Заполненный план объясняет продукт за секунду; пустой онбординг — нет. |
| Полоса зон в шапке карточки вуза | Даёт увидеть расклад приоритетов, не раскрывая карточку. |
| Метка «Демо» на каждой тестовой цифре | Единственное, что отличает честный прототип от вранья на защите. |
| Топ сравниваемых пар в аналитике | Показывает, между чем люди реально выбирают: отсюда берутся идеи для редакционных текстов. |

## Продукт: что убрали

| Убрали | Почему |
| --- | --- |
| Каталог всех вузов с фильтрами | Есть у всех конкурентов и не помогает принять решение. Поиск оставлен, но как инструмент внутри сценария. |
| Профориентационные тесты | Есть у Vuzopedia и Postupi; к вопросу «как не остаться без бюджета» отношения не имеют. |
| Подачу документов и вход через Госуслуги | Это работа суперсервиса Госуслуг. Дублировать её — значит конкурировать с государством в том, в чём оно уже работает. |
| Проценты «шанс 55%» | См. выше: посчитать честно нельзя. |
| Drag-and-drop приоритетов | Неудобно на телефоне, недоступно с клавиатуры. Кнопки ↑ ↓ работают везде. |
| Регистрацию и аккаунты | Для ценности не нужны, а персональные данные создают риски по 152-ФЗ. |
| Рейтинг вузов по «качеству» | Открытой метрики, которой можно доверять, нет. Придумывать её — обманывать. |
| Сравнение по «престижу» и отзывам | То же: непроверяемые данные в решении на всю жизнь. |
| Длинный лендинг с маркетинговыми блоками | Первая версия входного экрана была на три раздела со сравнительными таблицами. Для MVP это шум: остался один экран с одним действием и объяснением зон. |

## Технические решения

| Решение | Почему |
| --- | --- |
| Алгоритм в `packages/core` как чистые функции | Считается одинаково в браузере и на сервере, покрывается тестами без UI, проверяется инвариантами на случайных данных. |
| Расчёт плана в браузере | Весь сценарий работает без сети после первой загрузки. Для абитуриента с плохим мобильным интернетом это разница между «работает» и «нет». |
| Снимок данных в git | Расчёт воспроизводим, изменение данных видно в diff и проходит через CI. |
| Генератор демо-данных с фиксированным seed | Демо-сценарий защиты воспроизводится при каждой генерации; CI сверяет сгенерированное с закоммиченным. |
| Вузы демо-сценария закреплены полностью | Иначе случайный набор направлений мог сломать сценарий защиты между прогонами генератора. |
| Hono вместо Express и Nest | Один процесс на 12 эндпоинтов; `app.request()` тестирует без сокета. |
| Один процесс отдаёт и статику, и API | `docker run` одной командой без обратного прокси и compose. |
| План хранится как раскладка из идентификаторов | Зоны и предупреждения пересчитываются каждый раз, поэтому не могут разойтись с данными. |
| Экраны и снимок — отдельными чанками | Первый экран 69 КБ gzip вместо 483 КБ: снимок на 2,6 МБ грузится только когда нужен. |
| Статистика снимка в отдельном `stats.json` | Числа на первом экране не должны тянуть за собой весь снимок. |

## Отклонения от ТЗ

Каждое — с причиной и последствиями.

### 1. `node:sqlite` вместо `better-sqlite3` + Drizzle

**ТЗ:** `better-sqlite3` и Drizzle.
**Сделано:** встроенный `node:sqlite` и тонкий слой запросов.
**Почему:** у `better-sqlite3` нативная сборка. На машине разработки она не собирается без
Visual Studio, а в Docker требует build-toolchain в финальном образе или сложного копирования
скомпилированного модуля. Со встроенным модулем прод-образ — это **один JS-файл и статика,
без `node_modules` вообще**.
**Последствия:** нужен Node 23+ (в образе `node:24-alpine`); Drizzle не используется, запросы
написаны руками в `apps/api/src/db.ts` — их девять, и они простые.

### 2. `node:24-alpine` вместо `node:20-alpine`

**Почему:** в Node 20 модуля `node:sqlite` нет вовсе, в Node 22 он под флагом. Прямое следствие
решения №1.
**Последствия:** образ 245 МБ при лимите ТЗ в 250 МБ — проверяется smoke-скриптом.

### 3. Синий затемнён: `#0066D6` вместо `#0077FF`

**ТЗ:** `--accent: #0077FF`.
**Почему:** `#0077FF` с белым текстом даёт контраст **4,13:1** — ниже порога WCAG AA (4,5:1).
Из-за этого axe находил нарушение уровня serious на каждой кнопке и каждой ссылке, а ТЗ требует
ноль таких нарушений. `#0066D6` — тот же оттенок, но **5,4:1** на белом.
**Последствия:** требование «0 нарушений serious» выполнено; визуально разница едва заметна.

### 4. Выбор предмета из альтернативы

**ТЗ:** «берётся лучший из сданных», затем проверяется минимум.
**Сделано:** сначала рассматриваются предметы, проходящие минимум, среди них берётся лучший.
**Почему:** буквальная формулировка отсекает абитуриента, у которого физика 65 при минимуме 70,
хотя информатика 50 при минимуме 40 подошла бы.
**Последствия:** надмножество — никого, кто реально проходит, алгоритм не отбрасывает.

### 5. `plan_edit` и `planb_open` вынесены из воронки

**ТЗ:** воронка по всем событиям раздела 8.
**Почему:** правка плана и переход в План Б случаются на любом шаге. В воронке они ломали
монотонность и давали конверсии больше 100%.
**Последствия:** воронка вложенная и честная; эти два события показаны отдельным блоком
«Действия вне воронки».

### 6. Достижения приведены к практике 2026 года

**ТЗ:** медаль, ГТО, волонтёрство, итоговое сочинение с отличием.
**Сделано:** медаль, олимпиады и конкурсы (не БВИ), ГТО, спортивный разряд от КМС, волонтёрство.
**Почему:** за итоговое сочинение баллы сейчас почти нигде не начисляют, а олимпиады
и спортивные достижения в перечнях есть у большинства вузов.
**Последствия:** на экране указано, что значения типичные и точные надо смотреть в перечне своего
вуза, а олимпиады уровня БВИ дают место вне конкурса, а не баллы.

### 7. Карточки вузов сворачиваются, план стал дашбордом

**Почему:** план из 5 вузов по 5 направлений давал страницу высотой 4000px при пустых боках
на десктопе.
**Последствия:** 2031px на десктопе, сроки и действия — в боковой колонке. Все данные на месте,
раскрытие в один клик, первая карточка открыта сразу.

## Что стоило бы сделать дальше

Честный список, если бы проект продолжился:

1. **Реальные проходные баллы** — руками для 20–30 вузов, на которые приходится основной поток.
   Инфраструктура для этого уже есть: `programs.real.json` перекрывает демо и снимает метку «Демо».
2. **Квоты и БВИ** — целевая, особая и отдельная квоты меняют расклад для тех, у кого они есть.
3. **Стоимость жизни в регионе** — сейчас сервис только предупреждает о переезде.
4. **Сроки по конкретным вузам** — даты приёма отличаются, сейчас показаны общие правила.
5. **Уведомления о допнаборе** — самое ценное продолжение Плана Б, но требует подписки и,
   значит, персональных данных: решение нужно взвешивать отдельно.
