# Алгоритм

Весь расчёт живёт в `packages/core` — это чистые функции без побочных эффектов. Одна и та же
функция считает план и в браузере, и на сервере (`POST /api/plan`), поэтому расхождений между
клиентом и бэкендом нет. Пороги и лимиты заданы в `packages/core/src/config/`.

Покрытие тестами — 99% операторов при пороге 95%. Кроме примерных тестов есть инвариантные:
400 случайных профилей и наборов данных проверяются на свойства, которые обязаны держаться всегда.

---

## 1. Балл абитуриента для программы

```
examScore(program, user) =
    сумма по трём экзаменам программы
  + min(achievementsBonus, 10)
```

Для экзамена с альтернативой («физика или информатика») берётся **лучший из подходящих**: сначала
рассматриваются предметы, сданные не ниже минимального порога программы, среди них выбирается
предмет с максимальным баллом. Если ни один не проходит минимум, берётся лучший из сданных — но
только чтобы объяснить пользователю причину отказа.

> **Отклонение от буквы ТЗ.** ТЗ говорит «берётся лучший из сданных, затем проверяется минимум».
> Такая формулировка отсекает абитуриента, у которого физика 65 при минимуме 70, хотя информатика
> 50 при минимуме 40 подошла бы. Мы выбираем подходящий предмет — это надмножество: никого, кто
> реально проходит, алгоритм не отбрасывает.

```
eligible = сдан каждый нужный предмет И каждый зачтённый балл ≥ minScores
```

Неподходящая программа не попадает в план. В поиске она видна с причиной:
«Не подходит: нет физики» или «Не подходит: информатика ниже минимума 44».

**Пример.** Профиль: русский 78, математика 76, физика 70, информатика 72, знак ГТО (+2).
Программа 15.03.04 НГТУ: экзамены `математика, русский, [физика | информатика]`, минимумы 45 / 44 / 41 / 43.

```
математика   76  (≥ 45)
русский      78  (≥ 44)
информатика  72  (лучше физики 70, ≥ 43)
             --- 
examsSum    226
бонус        +2
итог        228
```

## 2. Прогноз проходного балла

```
trend            = clamp( ((c2025 − c2024) + (c2024 − c2023)) / 2 , −10, +15 )
predictedCutoff  = round( c2025 + trend )
margin           = examScore − predictedCutoff
```

Если известны не все годы — считаем по тем, что есть. По одному году `trend = 0`. Если проходных
нет вообще, зона не считается: программа показывается без зоны, а не с выдуманным числом.

**Пример.** Проходные 15.03.04: 2023 — 214, 2024 — 220, 2025 — 225.

```
trend = ((225 − 220) + (220 − 214)) / 2 = 5,5
predictedCutoff = round(225 + 5,5) = 231
margin = 228 − 231 = −3
```

Клампинг нужен, чтобы единичный скачок (например, вуз в один год сократил набор) не превращался
в прогноз «+40 за год».

---

## 3. Зоны

| Запас баллов | Зона | Что показываем |
| --- | --- | --- |
| `margin ≥ +10` | `safe` | **Запасной** |
| `−5 ≤ margin < +10` | `target` | **Цель** |
| `margin < −5` | `reach` | **Мечта** |

Пороги — `ZONE_THRESHOLDS` в `packages/core/src/config/zones.ts`. Границы проверены тестами
на значениях −6, −5, +9, +10.

**Почему зоны, а не проценты.** Чтобы посчитать вероятность поступления, нужны распределение
баллов подавших, число согласий и динамика отзывов заявлений. Ни одного из этих наборов в открытом
доступе нет. Любой процент был бы выдумкой, а решение принимается один раз в жизни. Поэтому
показываем запас баллов — величину, которую видно и можно проверить.

## 4. Сборка плана

`buildPlan(user, programs, universities)` работает в пять шагов.

### 4.1. Фильтрация

Остаются программы, которые:

- находятся в выбранных регионах (или где угодно, если выбрано «Где угодно в России»);
- попадают в выбранные группы интересов (первые две цифры кода — УГСН);
- подходят по экзаменам (`eligible`) и имеют посчитанную зону.

### 4.2. Оценка вузов

Каждый вуз получает рейтинг:

| Слагаемое | Вклад | Зачем |
| --- | --- | --- |
| есть `safe`-программа | +100 | подушка — главное, что даёт план |
| есть `target` | +60 | там и решается конкурс |
| есть `reach` | +10 | мечта ничего не стоит |
| число подходящих программ | +6 за каждую, максимум 5 | больше приоритетов в одном заявлении |
| попадание в интересы | +12 за место интереса | первый интерес важнее третьего |
| закрывает несколько интересов | +15 за каждый | разнообразный набор в одном вузе |
| есть направление «ровно под балл» | до +20 | `max(0, 20 − |margin|)` у лучшего попадания |
| свой регион | +40 | не нужен переезд |
| близость к центру своего региона | до +25 | `max(0, 25 − км / 60)` |

Точка отсчёта близости — средние координаты вузов домашнего региона, а не случайный вуз: в большом
регионе случайный вуз может стоять на краю, и расстояния получатся бессмысленными.

### 4.3. Выбор до 5 вузов

Сначала гарантируются два вуза с подушкой (в разных вузах — это условие вердикта «Бюджет почти
гарантирован»), затем вуз с мечтой, если её иначе не было бы в плане, дальше — по рейтингу.

### 4.4. Выбор до 5 направлений внутри вуза

Слоты делятся между интересами по важности: при трёх интересах и пяти слотах — 2 / 2 / 1. Внутри
интереса берётся самое **полезное**: сначала «Цель» (там решается конкурс), затем «Мечта», затем
«Запасной»; при равной зоне — то, что ближе к прогнозу проходного.

Потом состав достраивается: если подушки в наборе нет, а у вуза она есть — она вытесняет наименее
полезное направление. То же для мечты. Гарантированные направления защищаются от вытеснения, иначе
вторая гарантия отменяла бы первую.

Без раздачи слотов план получался из пяти почти одинаковых направлений одной группы — это было
видно на демо-профиле и исправлено.

### 4.5. Порядок приоритетов

```
сортировка: место интереса ↑, затем желанность зоны (reach → target → safe),
            затем меньший запас, затем код направления
```

Нумерация после сортировки и есть приоритет. Приоритет 1 подписан словами «Хочу больше всего» —
это то, чего абитуриенты не понимают в формулировке «приоритет».

---

## 5. Вердикт

| Условие | Вердикт | Цвет |
| --- | --- | --- |
| ≥ 2 вузов с `safe` | Бюджет почти гарантирован | зелёный |
| 1 вуз с `safe` | Бюджет вероятен, но добавь ещё запасной вариант | жёлтый |
| нет `safe`, есть `target` | Рискованно: все варианты впритык | жёлтый |
| только `reach` | Высокий риск остаться без бюджета | красный |
| план пуст | Под твои баллы бюджетных мест не нашлось | ведёт в План Б |

Цвет — всегда дополнение к слову: рядом с точкой стоит текст, а вердикт сформулирован фразой.

---

## 6. Предупреждения

| Идентификатор | Когда появляется | Текст |
| --- | --- | --- |
| `no_safe` | в плане нет ни одной `safe` | «Добавь запасной вариант — направление с запасом от 10 баллов» |
| `safe_above_reach` | приоритет 1 — `safe`, ниже есть `target`/`reach` | «Направления ниже приоритета 1 никогда не сработают, если ты проходишь на первое» |
| `few_universities` | вузов меньше 3, а доступные есть | «Можно подать ещё в N вуза — это бесплатно увеличивает шансы» |
| `several_regions` | вузы из разных регионов | называет регионы и напоминает про общежитие и дорогу; отдельная формулировка, если подушка только в чужом регионе |

Метка «Демо» к предупреждениям не относится: тестовые проходные помечаются отдельно на самой цифре.

---

## 7. Симуляция «Что будет, если…»

Для каждого вуза строится цепочка по приоритетам:

```
Приоритет 1 (Мечта)   · 09.03.04 — вероятно не пройдёшь
Приоритет 2 (Цель)    · 15.03.04 — на грани
Приоритет 3 (Запасной)· 13.03.02 — проходишь
=> Скорее всего зачислят на: 13.03.02 · Электроэнергетика и электротехника
```

Это не вероятностная модель, а следствие правила приёма: зачисляют на высший приоритет, по которому
абитуриент проходит. Если подушки в вузе нет, так и написано: «если не пройдёшь по мечте,
зачисления не будет».

---

## 8. Что алгоритм не делает

- Не считает вероятность поступления и не показывает проценты.
- Не учитывает целевую, особую и отдельную квоты, БВИ и внутренние экзамены — только общий конкурс.
- Не знает о стоимости жизни в регионе: про переезд только предупреждает.
- Не использует историю конкретного абитуриента и не сохраняет её нигде, кроме его браузера.
- Не ранжирует вузы по «качеству образования»: такой открытой метрики, которой можно доверять, нет.

---

## 9. Инварианты, закреплённые тестами

На 400 случайных мирах (профили, вузы, программы, регионы) проверяется:

- в плане не больше 5 вузов и не больше 5 направлений в каждом;
- приоритеты идут подряд с единицы;
- нет повторов вузов и направлений, направление всегда принадлежит своему вузу;
- в плане только подходящие программы, зона и запас совпадают с пересчётом;
- регионы и интересы пользователя соблюдены;
- если у выбранного вуза есть подушка или мечта — они остались в плане;
- вердикт согласован с составом зон;
- предупреждение «нет запасного» появляется тогда и только тогда, когда его действительно нет;
- симуляция описывает каждый вуз и все его приоритеты;
- повторный вызов на тех же данных даёт тот же план.
